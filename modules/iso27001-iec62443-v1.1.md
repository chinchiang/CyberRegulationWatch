## 二、Inventec 角色權重

角色權重屬於**預設報告篇幅配置**，不是排除規則，不得因篇幅權重而漏報 P0／P1。

### 主要角色

1. **Product Developer／Maintainer — IEC 62443-4-1**
   - 適用於產品 secure development lifecycle、維護及退役流程。
2. **Component Supplier — IEC 62443-4-2**
   - 適用於 embedded device、host device、network device 及 software application 之
     component security capabilities。
3. **System Product／Automation Solution Supplier — IEC 62443-3-3**
   - 僅在英業達實際交付物構成完整 system／Automation Solution，且合約、架構及驗收
     邊界支持該角色時適用。
   - 不得因提供單一 component、server、firmware 或 ODM 製造服務，即自動推定承擔完整
     IEC 62443-3-3 system conformity。

### 次要角色

4. **Asset Owner／Operator — IEC 62443-2-1、2-2、2-3、3-2 及部署相關 3-3**
   - 適用於英業達自有廠區 OT／IACS、製造設備及營運環境。
5. **Enterprise ISMS — ISO/IEC 27001 Family**
   - 適用於公司治理、驗證範圍、供應商、事件、BCP、內稽及管理審查。

### 例外角色

6. **Service Provider／Integrator／Maintenance Provider — IEC 62443-2-4、6-1**
   - 依實際客戶專案、合約、系統整合、遠端維護及服務範圍判定。
   - 不得預設為「極少」而忽略既有或新簽署的服務責任。

### Asset Owner 主題升級條件

與 Product Supplier 無直接關係之 Asset Owner 議題，原則上精簡呈現；但符合下列任一條件時，
必須進入主報告，不得只以一行帶過：

- P0／P1；
- 影響人員安全、工廠營運或 production continuity；
- 影響 OT remote access、legacy assets、backup／restore 或 incident response；
- 影響 NIS2／Czech Cybersecurity；
- 影響既有或規劃中 site／asset-owner certification；
- 形成重大客戶、Cyber Insurance 或主管機關要求。

產品線：

- Server／AI Server
- Notebook／PC
- Networking Equipment
- IoT／Smart Devices
- Automotive and industrial-related products

組織：

- GISMD／HQ IT
- EBG、PSG、NBG
- PSIRT／CSIRT／SOC
- OT／Manufacturing／Facility
- R&D／Quality／Regulatory／Legal
- Procurement／Supplier Management

據點：

- 臺灣
- 捷克（Inventec Czech／ICZ）
- 美國
- 墨西哥
- 其他海外據點

中國上海與重慶屬法律隔離區。涉及中國區 log、個資、產品漏洞、事件資料、原始碼、
設計文件或供應商資訊時，標示：

`CHINA LEGAL REVIEW REQUIRED`

不得在未經 Legal 評估及正式授權下要求跨境調取或匯出。

## 三、角色與標準適用框架

| 角色 | 核心標準 | 主要問題 |
|---|---|---|
| Enterprise ISMS | ISO/IEC 27001、27002、27005、27035、27036 | 治理、風險、控制、事件、供應商、持續改善 |
| IACS Asset Owner／Operator | IEC 62443-2-1、2-2、2-3、3-2、3-3 | OT Security Program、legacy、zones/conduits、SL-T |
| Service Provider／Integrator／Maintenance | IEC 62443-2-4、6-1 | 整合、維護、遠端服務、變更、服務能力 |
| System Designer／Integrator | IEC 62443-3-2、3-3 | SUC、risk assessment、zones/conduits、SL-T／SL-C |
| Product Developer／Maintainer | IEC 62443-4-1 | Secure PDLC、verification、defect、patch、EOL |
| Component Supplier | IEC 62443-4-2、6-2 | Embedded／host／network／software component security capabilities |
| System Product／Automation Solution Supplier | IEC 62443-3-3 | System requirements、SL-C(system)、integration boundary、acceptance evidence |
| Conformity Assessment Body | IECEE、ISASecure、ISO/IEC 17000 系列 | Scope、評估方法、證書效力與承認 |
| Accreditation Body | ISO/IEC 17011、Global ACI MRA 及區域安排 | CAB competence、MRA recognition、transition 及 scope |

### 禁止推論

違反下列任一規則即為報告缺陷：

- 不得將 Asset Owner 義務套用於 Product Supplier。
- 不得將 Product Developer／Supplier 義務套用於 System Integrator。
- 不得將 Component certification 寫成整個 system、Automation Solution 或工廠已合規。
- 不得將 IEC 62443-4-2 certificate 延伸為 IEC 62443-3-3 system conformity。
- 不得將取得 ISO/IEC 27001 或 IEC 62443 證書寫成已自動符合 CRA、NIS2、捷克法、
  RED DA 或客戶合約。
- 不得因品牌、出貨、製造或 ODM 身分，自動推定英業達為法定 Manufacturer、
  Product Supplier 或 System Integrator。
- 不得將 certification scheme requirements 寫成 IEC normative requirements。
- 不得將某一 scheme owner 之 commentary 寫成另一 scheme 之 normative rule。
- 不得依 Wikipedia、彙整站或部落格提出組織性主張（例如某分冊「無某組織參與制定」）。

### C. 符合性評鑑與認可制度

#### ISASecure

追蹤：

- SDLA／CSA／ICSA／SSA scheme 文件版本；
- ACSSA 場域評鑑與人員資格；
- Certification Body 及 laboratory 名單；
- 已認證產品、process 及 certificate status；
- Security Maintenance Audit 及 surveillance 要求；
- certificate scope、target SL、exceptions 及 extensions。

ISASecure 官方 scheme commentary 曾指出：

- ISASecure 通常採預先定義之 assurance structure，要求評估 target SL 下所有 applicable requirements；
- IECEE 可能允許較彈性的 evaluation scope。

但此資訊屬 scheme-owner commentary，不得直接寫成 IECEE normative rule。每案仍須以：

- ISASecure scheme document；
- IECEE Operational Document；
- Test Report Form；
- Certification Body proposal；
- final certificate scope

逐案確認。

#### IECEE

追蹤：

- CB Scheme Operational Documents；
- Test Report Forms；
- IEC 62443 evaluation scope rules；
- certificate database；
- issuing NCB／CBTL；
- standard edition 及 certificate validity。

#### ISO/IEC Conformity Assessment Standards

追蹤：ISO/IEC 17011、17021-1、17025、17065、27006-1。

#### Global Accreditation Cooperation Incorporated（Global ACI）

- Global ACI 自 2026-01-01 全面運作，取代 IAF 與 ILAC；
  IAF MLA 與 ILAC MRA 同時併為單一 **Global ACI MRA**。
- IAF 及 ILAC 自 2026-01-01 不再營運；其網站作為 legacy／archival 站台。
- **不得一律宣稱所有 IAF／ILAC 文件已失效。** 依 **Global ACI Resolutions 2025-25 與 2025-29**，
  特定 IAF 與 ILAC 文件在對應之 Global ACI 文件通過採用前仍然有效。
  Global ACI 文件區並提供 **IAF／ILAC → Global ACI cross-reference table**。
- 引用舊 IAF／ILAC 文件時，必須逐份確認：
  1. 是否已由 Global ACI 文件取代（查 cross-reference table）；
  2. 是否被 Resolutions 2025-25／2025-29 保留；
  3. 是否已被明文撤回；
  4. 是否僅適用於已結束之 transition event；
  5. 是否仍被相關 AB、regional body 或 scheme owner 採用。
- IAF MD 29:2024 可用作 ISO/IEC 27006-1:2024 transition 要求及歷史依據，
  但其 2026-03-31 期限已屆滿。

**Mark Transition（v1.1 新增）**

- IAF MLA Mark 已授權予 Global ACI，於新的 **Global ACI MRA Mark** 推出前仍然有效。
- 2025-12-31 前已為 IAF MLA／ILAC MRA signatory 且已簽署授權協議之 CAB，
  可於過渡期繼續使用舊 Mark；Global ACI MRA Mark 可用後須依公告程序轉換。
- 自 2026-01-01 起，AB 原則上不再受理新的 IAF MLA Mark 授權申請。
- **判讀規則**：供應商或英業達證書上出現 IAF MLA Mark，**不等於證書失效或未轉換**。
  客戶稽核提問時，應以 CB 之 Global ACI MRA signatory 狀態及 AB scope 回答，
  不得以 Mark 圖樣作為有效性判準。
- Mark 轉換里程碑列入 Deadline Radar 之 `Mark Transition` 類別。
- IAF CertSearch 目前仍可使用；持續監控其品牌、治理、資料所有權及繼受平台安排。

區域及國家認可機構：APAC、EA、TAF（臺灣）、ČIA（捷克）、ANAB（美國），
以及其他英業達實際 Certification Body 所屬之 Accreditation Body。

### D. 供應鏈與產品責任（SBOM／VEX／CSAF／SDLC）

#### CISA 2026 Minimum Elements for SBOM `[V]`

- Published：2026-07-29。
- 取代 2021 NTIA Minimum Elements 作為新的美國政府 SBOM baseline guidance。
- 共同發布／參與機關包括 NÚKIB、ANSSI、BSI、METI 及其他國際夥伴
  → 直接連動模組 02（CRA）與模組 03（NIS2／捷克）。
- 適用範圍涵蓋 open-source software、AI software 及 SaaS。
- 新增或強化之資料包括：
  - component hashes 及 hash algorithm；
  - component license；
  - SBOM generation tool name 及 version；
  - generation context；
  - SBOM format name 及 version；
  - SBOM version；
  - SBOM author signature／digital-signature related field。
- 缺漏資訊須明確區分 `unknown` 與 known but purposefully withheld／`redacted`。
- 不得在沒有正式文字支持時，將通用 `N/A` 與上述狀態視為同一規則。
- 此文件為 government guidance；除非被法律、採購契約、客戶規格或 certification scheme 採用，
  不得寫成普遍適用之 binding requirement。

#### G7 Software Bill of Materials for AI — Minimum Elements `[U]`

- Published：2026-05。
- 屬 G7 partner guidance，聚焦 AI system supply-chain transparency。
- 追蹤 model、dataset、software component、provider、license 及 AI-specific dependencies。
- 屬 voluntary guidance，除非被法規、客戶或採購契約採用，不得寫成 binding requirement。

#### CSAF／VEX

- **ISO/IEC 20153:2025 — Published** `[V]`
  - 對應 OASIS CSAF v2.0 Specification，Edition 1、2025-02、115 頁、Stage 60.60。
  - 經 ISO/IEC JTC 1 之 PAS procedure 採納。
  - 可承載 security advisory 及 VEX profile。
  - **可自 ISO 及 IEC webstore 免費取得（CHF 0）**，
    因此可直接於 PSIRT 程序、客戶合約及技術文件中引用，無須採購預算。
- **OASIS CSAF v2.1 — Under development** `[U]`
  - 截至基準日為 Committee Specification Draft 02。
  - 尚非 OASIS Standard，也不是 ISO／IEC International Standard。
- 每週監控：OASIS approval status；v2.0／v2.1 schema compatibility；VEX profile changes；
  tool-chain support；是否進入 ISO／IEC fast-track 或其他國際標準程序。

#### SBOM 格式及產品維護

追蹤：CycloneDX、SPDX、VEX profiles 及承載方式、62443-4-1 Defect Management（DM）、
62443-4-1 Security Update Management（SUM）、PSIRT 與 security advisory 之 CSAF publishing、
SBOM signing／provenance／versioning／distribution、support period、EOL／EOS 及
unsupported component 處理。

### E. 產業與客戶 Flow-down

#### SEMI

SEMI 標準採 `-YYMM` 版次碼。**所有 SEMI 條目必須記錄版次碼**，否則無法辨識 Delta。

- **SEMI E187 — Specification for Cybersecurity of Fab Equipment** `[U]`（版次碼待確認）
  - Fab equipment cybersecurity baseline。
  - 核心 normative scope 聚焦 fab equipment 中搭載 Windows／Linux 之 computing devices。
  - 原標準範圍不應自動延伸至 PLC、SCADA computing devices 及 sensor-actuator network devices。

- **SEMI E188 — Malware Free Equipment Integration** `[U]`（版次碼待確認）

- **SEMI E191 — Computing Device Cybersecurity Status Reporting** `[V]`
  - **現行版次：E191-0326（Current）；E191-1024 已 Superseded。**
  - Scope：適用於任何連接廠務網路、且由 equipment supplier 隨製造設備提供之 computing device，
    例示包含 computer、Equipment Control System（ECS）、programmable logic controller（PLC）。
  - **範圍排除**：MES、MCS 及其他由工廠自行提供之 computing devices 不在本標準範圍內。
  - 不得把 E187 的 scope exclusion 錯誤套用到 E191；兩者排除規則不同。
  - 追蹤 CDS Task Force 對 OS patch／service pack／installed component 之擴充，
    以及非 SECS-II 之替代回報機制（gRPC、Protocol Buffers、XML／JSON）。

- **SEMI E191.1 — SECS-II Protocol for Computing Device Cybersecurity Status Reporting** `[V]`
  - 為 E191 之 subordinate standard，僅做 SECS-II 對映，不新增概念模型。

## 五、ICS 漏洞納入條件

一般 ICS CVE／KEV 不進本模組，標註：

`已由日常 CTI 巡邏涵蓋`

僅下列情況納入，且必須從標準、certificate、contract 或 governance obligation 角度撰寫：

- **V1**：影響已取得 ISASecure／IECEE 或其他 IEC 62443 認證之產品，
  可能牽動 certificate scope、maintenance obligation 或 market claim。
- **V2**：暴露 IEC 62443-4-1 defect management、patch management 或 security update process
  之系統性落差。
- **V3**：客戶據此發出 security questionnaire、audit request 或變更合約條款。
- **V4**：主管機關、Accreditation Body、scheme owner 或 Certification Body 據此發布指引，
  改變 ISO/IEC 27001 或 IEC 62443 稽核查核點。
- **V5**：漏洞導致 certificate suspension、withdrawal、scope reduction、mandatory reassessment
  或 product release blocker。

## 九、證據與防幻覺規則

1. 標準名稱、編號、年份、edition、Amendment、Corrigendum 及 publication status，
   必須以官方來源核實。
2. 不得推估尚未發布標準之正式編號、發布日或內容。
3. Draft／WD／CD／DIS／FDIS／PAS／TS／TR／International Standard 必須分開標示。
4. 不得將草案寫成最終要求。
5. 不得將 official FAQ、webinar、blog 或 Certification Body 解讀寫成 normative requirement。
6. 不得將 scheme-owner commentary 寫成另一 scheme 之 normative rule。
7. 不得將廠商 self-declaration 寫成 third-party certification。
8. 不得因供應商持有 ISO/IEC 27001 certificate，即推定其全部產品、服務、sites 或
   subsuppliers 均在 scope 內。
9. 不得因產品取得 IEC 62443-4-2 component certificate，即推定其 Automation Solution、
   system 或 deployment environment 符合 IEC 62443-3-3。
10. 不得因 IEC 62443-4-1 process certificate，推定所有產品均已完成 4-2 或 3-3 conformity。
11. 不得宣稱 ISO／IEC certification 自動滿足 CRA、NIS2、RED DA 或其他法律。
12. 不得大量重製受著作權保護之標準條文；僅提供 requirement ID、主題、摘要及 impact analysis。
13. 無法存取 normative text 時標示 `[NORMATIVE TEXT NOT AVAILABLE]` 或
    `[OFFICIAL METADATA VERIFIED ONLY]`。
14. Overview／terminology 文件發布（例如 ISO/IEC 27000:2026），預設不構成
    certification obligation 變化，除非能指出 ISO/IEC 27001 條款、CAB rule 或
    scheme rule 同步變動。
15. 僅見於 Tier 3 之版次發布主張而 Tier 1 無法確認者，列入「待查證主張」，禁止進主體。
16. 引用 IAF 或 ILAC 文件時，不得一律宣稱文件失效；必須依 Global ACI Resolutions
    2025-25／2025-29 及 cross-reference table，查核其是否被明文撤回、保留或已被取代。
17. Standard stability date、systematic review date、transition deadline 及
    PAS automatic withdrawal 必須分欄記錄，不得混用。
18. Certificate 須以 certificate number、scheme、edition、entity、product／site／process、
    version、SL、CB、AB、issue date、expiry 及 public source 逐項確認。
19. Internal certificate、audit finding 及 customer contract 須遵守文件密級，
    不得置於公開網站。
20. 篇幅由 Delta 數量決定；零 Delta 週可精簡，但必須交付具體 Stability Confirmed
    及 source coverage。
21. 發現先前報告錯誤時，必須輸出 `CORRECTION`，說明 incorrect prior statement、
    corrected fact、root cause、affected decisions／actions 及 State File correction。
22. 已知錯誤案例：
    - 「IEC 62443-4-2:2026 於 2026-06-01 發布」之主張，若 IEC Webstore 仍僅顯示 2019 版，
      必須列為 Tier 3 未證實內容；
    - 將 IEC TS 62443-6-2 誤寫為 62443-8-2，視為 standard identifier defect。
23. **原版優先與 national adoption 規則（v1.1 新增）**
    - 所有 edition、publication date、page count 一律以 IEC／ISO 原版為準，
      並於 State File 標註 `source_edition`。
    - 國家或區域採用版（BSI PD、DS、ČSN、CNS、ANSI/ISA、EN 等）之日期、頁數或
      編號差異，屬 national adoption artefact，**不得計為 Delta**，
      亦不得據以觸發 Flash Alert。
    - 僅在該採用行為本身構成英業達義務時（例如 CNS 或 ČSN 被主管機關或客戶引用），
      另立 `national_adoption` 項目追蹤。
24. **可稽核性規則（v1.1 新增）**
    - State File 每一標準列必須具備 `source_url`、`source_edition`、`verified_by`。
    - 缺少上述任一欄位者，其 `last_verified_at` 視為未完成核實，
      標示 `CARRIED FORWARD — NOT RE-VERIFIED`，不得計入 Stability Confirmed。

Mark 判讀：證書上出現 IAF MLA Mark 不得逕行判定為失效或未轉換，
須以 CB 之 Global ACI MRA signatory 狀態及 AB scope 為準。

### 8. Cross-Regulation Dependency

`Standard Requirement｜CRA｜NIS2／Czech｜RED DA｜AI Act｜
Customer Contract｜Reusable Evidence｜Conflict／Gap｜Decision`

必須區分：Legal requirement／Harmonised standard 之 presumption of conformity／
Official recommendation／Contractual requirement／Certification scheme requirement／
Voluntary best practice。

不得將 voluntary standard 寫成 binding law。

- ≤30 days
- 31–90 days
- 91–180 days
- >180 days

- External／Certification Deadline
- Legal Deadline
- Customer Deadline
- PAS Automatic Withdrawal
- Stability／Systematic Review Date
- **Mark Transition**（IAF MLA Mark → Global ACI MRA Mark）

## 十一、優先級

### P0

- 現行標準遭撤回、取代或修正，立即影響既有 certificate、產品上市、
  客戶合約或 regulatory programme。
- Certificate 遭 suspension、withdrawal、expiry 或 scope reduction。
- Certification、customer 或 legal deadline 在 30 日內且未完成。
- 重大客戶要求立即提供 ISO／IEC 62443 evidence。
- 發現產品、supplier 或 site certificate claim 錯誤、過期或無法驗證。
- 標準變更直接影響 CRA、NIS2、RED DA、product release 或工廠營運。
- 發現 system／component role 誤判，且已影響合約、certificate claim 或 technical documentation。

### P1

- 31–90 日內之 transition、audit、certification 或 contract deadline。
- 新標準或 scheme 造成重大 policy、SDL、OT architecture、supplier contract 或 evidence gap。
- 需要 GISMD、BU、Legal、Quality、Procurement 或 Management 決策。
- Hot List 出現新版、DIS／FDIS 狀態重大進展或 scheme scope change。

### P2

- 91–180 日內之制度、認證、供應商或產品改善。
- 尚未強制，但高度可能影響下一次 audit、customer review 或 product roadmap。

### P3

- 長期標準發展、early draft、一般產業動向、第三方評論、
  尚未形成英業達 applicability 之 best practice。

## 十二、Out-of-Cycle Flash Alert

發生下列情形時不等待週一：

1. ISO/IEC 27001 或核心 IEC 62443 分冊正式發布新版、撤回或重大 Corrigendum。
2. Certification／accreditation transition 期限或規則出現重大變更，
   包括 Global ACI MRA、Resolutions 2025-25／2025-29 之變動及 MRA Mark 推出。
3. 英業達 certificate 遭 suspension、withdrawal、scope reduction 或 major nonconformity。
4. 主要客戶新增具期限之 ISO/IEC 27001 或 IEC 62443 flow-down requirement。
5. CRA、NIS2、RED DA 或其他法律正式引用相關標準並改變 compliance route。
6. IECEE 或 ISASecure scheme 出現影響既有或規劃中 certificate 之重大變更。
7. 產品或供應商 certificate 被發現無效、過期、錯誤引用或與實際版本不符。
8. 標準變更可能阻擋 product release、工廠驗收、customer audit 或重大採購。
9. 發現先前報告存在可能影響管理決策之重大 standard identifier、edition、
   document-type 或 role-mapping 錯誤。
10. P0 item 在首次 Baseline Snapshot 即被發現。

**不觸發 Flash Alert 之情形**：僅因國家或區域採用版之日期、頁數、編號差異
而產生的表面變動（見防幻覺規則 23）。

Flash Alert 內容：

`Confirmed Facts｜Standard／Scheme Status｜Affected Role｜
Affected Site／Product｜Immediate Risk｜Decision Required｜
Next Action｜Owner｜Deadline｜Unknowns｜Source Tier｜Admiralty`

## 執行前提

1. 必須啟用即時網路搜尋。
2. 無法聯網時停止標準狀態判定並回報，不得以既有知識推估 current edition、
   publication status、certificate status 或 transition rule。
3. 首次執行採 Baseline Snapshot 模式：
   - 逐列查證 A–E 五軌之 current edition、document type、stage、
     publication／withdrawal date；
   - 產出 State File v1，每列補齊 `source_url`、`source_edition`、`verified_by`；
   - 產出 Source Coverage Statement；
   - 建立 Hot／Warm／Trigger-only 清單。
4. **首週 Baseline Snapshot 優先序**：先處理本文標示 `[U]` 之項目，依序為
   ISO/IEC 27018:2025、27009:2020、DIS 27007、FDIS 27028、ISO 27799:2025、
   ISO/IEC 27701:2025、IEC PAS 62443-1-6:2025 之頁數與發布日、
   IEC 62443-4-2:2019 之 2022 Corrigendum、G7 AI SBOM、OASIS CSAF v2.1、
   SEMI E187／E188／E191.1 版次碼。
5. 首次 Baseline Snapshot 原則上不輸出 §十之 1–9 與 12，但保留 **Critical Override**：
   若發現 P0、certificate 無效或過期、30 日內 legal／customer／certification deadline、
   重大錯誤 claim、product release 或 factory acceptance blocker，
   則必須同時輸出 Flash Alert、Decision Required 及最小 Action Register。
6. 第二週起進入 Delta 模式。
7. 每週不得直接複製上週 baseline；所有 current-status statement 均須有
   `last_verified_at`、`source_url` 及 `verified_by`。

   並禁止在未釐清前自行選擇其中一方。
